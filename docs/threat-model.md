# Threat model

## Assets

- **Session content**: prompts, code, tool output, images. It can contain secrets that the user pasted or a
  tool printed.
- **Working trees and clones** on development machines, which remote control and handoff change.
- **The host token**: full operator control (read, prompt, answer permissions, hand off, mint devices).
- **Scoped API tokens** ([ADR 0033](adr/0033-a-command-line-tool-an-sdk-and-scoped-tokens.md)): a secret for a
  script, limited to abilities, an allow-list of machines and projects and an expiry; stolen, it reaches no more
  than its grant.
- **Device tokens**: one per agent; enough to sync as that device and to receive its control messages.
- **Claude Code permissions**: a permission answer lets Claude Code run a tool on a development machine.
- **Permission rules** (planned, [ADR 0029](adr/0029-permission-rules-match-on-the-agent-and-deny-wins.md)): the allow, ask and deny rules that decide a
  tool call without the user; a rule that allows too much is a permission nobody answered.
- **A shell on a development machine**: with `terminal` on, the host token opens a shell as the agent's user
  ([ADR 0026](adr/0026-the-inspector-opens-a-restricted-terminal-and-links-dev-servers.md)).
- **The audit log** ([ADR 0030](adr/0030-the-audit-log-records-actions-in-a-hash-chain.md)): who answered a
  permission, switched a mode, minted a token or deleted a session, and the commands and changed paths of tool
  calls. Its value is that it is complete and unaltered; it holds commands, so it is as sensitive as the session
  file.
- **Hook secrets and hook scripts**: a hook's signing secret proves to a receiver that an event is
  Hoplet's; a script hook is a program the agent runs as its user on an event
  ([ADR 0031](adr/0031-the-session-lifecycle-events-and-the-two-hook-kinds.md)).

## Trust boundaries

- Browser ↔ core: the host token on REST; a single-use ticket on the browser WebSocket.
- Scripted client ↔ core: a scoped API token (`hpt_...`) on REST. Every route declares the ability it needs and is the host's alone
  otherwise, and the core checks the grant's allow-list on every session, machine and project the request names. A ticket carries the token's scope into the
  browser WebSocket.
- Agent ↔ core: a device token on the agent WebSocket.
- Core ↔ outside services: the core posts notifications to the push services of subscribed browsers and to the
  user's webhook URLs, the only connections it opens ([ADR 0021](adr/0021-notifications-and-signed-action-links.md)).
- Core ↔ hook receivers (ADR 0031): the core posts lifecycle events to the user's hook URLs, signed with a per-hook secret, an outbound
  request that is checked against private, link-local and metadata addresses before it is made.
- Anyone with an action link ↔ core: the two `/api/action/*` routes take a signed token instead of the host token.
- Reverse proxy ↔ core: plain HTTP on the host's loopback; the proxy terminates TLS.
- Contributors ↔ repository: the source is public and anyone can propose a change; only the maintainer merges.
- Core ↔ data directory: trusted when written, parsed defensively when read.
- Core ↔ agent control: a control message makes the agent start Claude Code, answer a permission, write a
  worktree and a session file, or delete a session file and a worktree it made. The agent accepts control only from the core it is configured for.
- Core ↔ agent terminal: when the agent's `terminal` switch is on, a control message makes the agent start a shell
  on a PTY and carry its input and output. The switch is read from the agent's own configuration, so the core cannot
  turn it on.
- Core ↔ agent rules (planned): the core pushes the rule set the agent evaluates; the agent applies it only from the
  core it is configured for, and its own `deny` rules are a floor the push cannot lower.
- Agent ↔ audit log (planned, ADR 0030): an agent can report facts of defined types about a session it owns (an
  automatic permission decision, a verification result); the core validates them, stamps the device and writes them.
  No message writes a record directly, and a session can neither read nor write the log.
- Core ↔ agent script hooks (ADR 0031): the agent runs an executable that the operator declared in its own
  `config.json`, on an event the core forwards by hook ID (`hook.event`), and checks the ID, the event type and the project again. No
  message carries a command, argument, environment variable or path, so the core cannot make the agent run anything
  the file does not name; `hook.result` returns only an exit code, a duration and 1 KiB of standard error.
- Hook process ↔ agent (Codex rule hook, [ADR 0032](adr/0032-codex-rule-hook-calls-the-agent-over-a-local-socket.md)):
  the `hoplet-agent hook codex` process Codex starts for each tool call asks the agent for the decision over the Unix
  socket `<hoplet_home>/hook.sock` (directory 0700, socket 0600). The agent accepts only the agent's own user ID
  (peer credentials) and a per-process nonce that it maps to the session; the session ID, working directory and mode
  in the hook input are ignored. An unknown nonce, a missing socket, a bad reply or a timeout is a deny. It protects
  the decisions and the permission cards from other users and from processes without the nonce; it does not protect
  against a process running as the same user, which can read the nonce or use the socket, the same as the provider's
  own configuration files.
- Agent ↔ Claude Code: the agent reads the session file and the streaming output as untrusted data and
  never executes their content.
- Agent ↔ filesystem: request paths, snapshot entries and git output are untrusted until resolved inside
  their root.

| Token theft on the network | browser/agent ↔ core | TLS at the proxy; compose publishes only on `127.0.0.1`; no token in any URL | `image/compose.yaml` review; `core/test/auth.test.ts` |

| Remote prompt, permission answer or new session by an attacker | browser ↔ core ↔ agent | Requires the host token; every prompt and answer is logged with session ID and `promptId` or `requestId`, a new session with device, project path and `promptId`, never content. A Codex process runs in the session's directory with the agent's environment and the user's own Codex login; image files for a prompt are written under `<hoplet_home>/codex-images/` (mode 0600) and removed when the process exits. | Provider configuration turns the host token into code execution or leaks a key | browser ↔ core ↔ agent | A configuration's `command` and environment variables are written only on the machine (`providers.json`, mode 0600, or `hoplet-agent provider`). | Permission rules allow what the user did not mean | model ↔ agent | A rule decides on the agent ([ADR 0029](adr/0029-permission-rules-match-on-the-agent-and-deny-wins.md)). A command is parsed into simple commands; one with shell control (`;`, `&&`, `\|\|`, `\|`, backticks, `$(`, redirections, newlines, heredocs, leading assignments, expansions or globs in the command word, or text that does not parse) is never allowed by an `allow` rule, and `deny` and `ask` rules see every simple command in it and through the wrappers `env`, `sudo`, `xargs` and `sh -c`; an `allow` is anchored at the first word, so a wrapper or an alias does not inherit it. Paths are made absolute and cleaned, symlinks are resolved (for a new file its nearest existing parent), matching is by whole path segment and ignores case where the filesystem does, a `deny` matches either the written or the resolved path, an `allow` only the resolved one. Domains are the exact lowercase host of the URL. Precedence is fixed: a `deny` at any scope wins, then the narrowest scope, `ask` before `allow`. A command rule is a guard against mistakes, not a sandbox: a program the model writes and runs, or a path built at run time, is not seen. The provider's sandbox and the machine's own permissions stay the boundary. Rules act through the provider's pre-tool hook; Codex skips a hook that is not trusted without a message, so the agent registers its hook with `bypass_hook_trust` for its own sessions and logs when a command or file change ran without the hook having been asked; the session shows a note that its rules were not enforced under that call, and one at the start of a `rules: prompts-only` transcript. The agent takes the permission mode from its own state, not from the hook's input. The agent answers the hook itself, in Claude Code through the permission callback and in Codex over `hook.sock`: a call it cannot read is denied, an `allow` is not given in plan mode (Codex decides there), a hook that runs and cannot reach the agent, errors or gets no answer denies (the hook prints its deny at 870 s and the agent resolves an unanswered `ask` as a deny at 860 s), and the log names a failure without the call's content. Residual risk, checked against Codex 0.163.0: Codex supports only `deny` from the hook and fails open, so a hook process that cannot start, is killed or outlives Codex's 900 s timeout lets the call run under Codex's own approval policy and sandbox, and an `allow` or an approved `ask` prints nothing and leaves the call to that policy. The rules then do not hold against anything that stops the hook process, such as a program of the same user killing it Where the agent cannot check who connects to the socket (Windows) it opens none, runs Codex without the hook and declares `rules: prompts-only` | built for Claude Code and Codex sessions with the rules the core sends and the floor |
| Rules tampered with or stale | core ↔ agent, agent ↔ filesystem | Rules arrive only as `device.rules` on the agent's authenticated connection to its own core, with a revision; the agent refuses unknown fields and applies the set whole or not at all, keeps the last applied set in `<hoplet_home>/permission-rules.json` (mode 0600) and answers `device.rules.applied`, so the core knows the revision each connected machine applied, and Settings lists the machines that have not. While disconnected the agent keeps deciding by the last set, so a rule deleted in the web still holds there until it reconnects, and each recorded decision (planned with the audit records) names the revision it used. A compiled-in deny of the Hoplet home and the provider settings and hook files, and the operator's `permission_deny` in the agent configuration, hold against any push, and a push cannot add an `allow` over them. A holder of the host token can still change rules, turn defaults off (after a second confirmation) or switch to Bypass permissions: rules protect against a model's slips and injected instructions, not against the operator | built: the push, the strict apply, the file and the floor; the display of unapplied revisions; the audit records planned with #98 |
| A session widens or removes its own rules | model ↔ core | No MCP tool and no route reachable with a session's token creates, changes or deletes a rule or a permission mode; a child session obeys its parent's `deny` and `ask` rules and gets no `allow` from them ([ADR 0029](adr/0029-permission-rules-match-on-the-agent-and-deny-wins.md)). Writes to the provider settings and hook files, where the rule hook is registered, are denied by the compiled-in floor | planned with #98 |
| The user is trained to answer "Always allow" | user ↔ core | The card only drafts a rule: the user edits it and scopes it to the session or the project (global is set in Settings only), a call with shell control, a plan exit or an unclassified tool gets no draft, and a draft starts as narrow as the request (the first words of a command, one file, one host). Every rule change and every decision by rule is marked in the conversation and recorded in the audit log with the rule ID, so a rule that allows too much can be found afterwards. Not a boundary: a user who accepts every draft has widened the rules as far as they chose | planned with #98 |
| Hostile or oversized images sent with a prompt | browser ↔ core ↔ agent ↔ Claude Code | Only with the host token and only to a machine whose driver declares `images`. ## Accepted risks

- **The host token is operator-level.** Whoever holds it can run Claude Code with tool permissions on every
  connected machine, and can turn the permission prompts off for any controlled session (Bypass permissions), and on a machine whose operator turned `terminal` on, can open a shell as the agent's user in a session's directory. Accepted because Hoplet has one operator; it is kept off the public internet without TLS. A stolen host token therefore is a shell on every machine with `terminal` on; turn it off on machines where that is not acceptable.
- **The server sees plaintext sessions and snapshots.** Accepted because the server is the user's own host.
- **A scoped token acts with the authority of its grant.** A token that may send can prompt a session on its allowed machines, and Claude Code then acts there as the machine's user within that session's permission mode; a token that may answer permissions can approve a tool call. The audit log names the token, not its holder. Grant `answer` and `create` only to clients that need them.
- **No rate limiting on the host token.** Accepted while the core is reachable only through the user's proxy. The action routes are the exception: they are rate limited because anyone who has the address can reach them.
- **A push service or a webhook sees that a session needs the user.** The payload is redacted and short, but the service learns the project name, the session title and the timing. Accepted because the user chose that service; a webhook can be pointed at a host of their own.
- **The audit log shows tampering; it does not prevent it** (ADR 0030). Someone with write access to the
  host can rewrite records and recompute every hash, replace the verifier, delete the newest records or substitute
  a consistent forgery. Only a copy of the head hash (`hoplet audit head`) kept off the host detects that; Hoplet
  sends it nowhere. Records name the host token and a channel, not a person: with one operator, the log cannot say
  which of several people used it. Scrubbing is pattern-based and misses an unnamed secret.
- **A hook receiver sees that a session did something.** Even without a summary it learns the project's name, the
  machine, the event type and the timing. Accepted because the user chose the URL.
- **Script standard error is not redacted.** The first 1 KiB of what a script writes is shown in the web UI to the
  holder of the host token. Accepted because the script is the operator's own.
- **A session running as the same user can write the agent's `config.json` and the scripts it names.** It can
  already write any file that user can; the boundary of script hooks is against the host token and the core, not
  against code on the machine.
- **A terminal Claude Code process can still write a session that Hoplet controls.** Hoplet detects foreign
  growth before it starts a process and reports `external`, but cannot stop a process it did not start.

## Out of scope

- Compromise of a development machine: its agent and Claude Code already read and write everything there.
- The reverse proxy, its TLS configuration and the network between the user's machines.
- Claude Code itself, and what a tool it runs does after the user allowed it.
